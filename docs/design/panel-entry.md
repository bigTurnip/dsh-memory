## 1. 事实基线：我核验过什么（以及没核验什么）

> **证据边界（必须先说清）**：下列插槽事实来自**本机已安装构建产物**（`/Applications/DeepSeek Harness.app/Contents/Resources/app.asar`，版本线 `0.2.1-rc.5`）内部的**插槽契约清单**与该清单指向的实现代码，以及包内 `ui-sidebar-right` 的公开文档。**我没有在运行中的 GUI 里实际看到面板被挂上去**——所以"能挂、怎么挂"是可引用的，而"挂上去的像素长什么样"列为 §13 的未验证项。

### 1.1 四个候选挂载位（逐条核验结果）

| 挂载位 | kind / scope | 宿主给什么 | 现有占用者 | 对记忆入口的关键含义 |
| --- | --- | --- | --- | --- |
| `sidebar.footer.action` | `list` / **root** | **只有 `{ wide: boolean }`**（`wide=false` 即 56px 折叠轨） | `cordis-panel`（插件面板） | **拿不到会话**。要按会话算任何东西，入口必须自己从 `useSessions` 派生"当前会话"（cordis 就是这么做的）。与 Settings 同处侧栏底部脚区 |

| --- | --- | --- |
| `conversation.chat.turnTail` | `list` / session；ownerProps `{ turn, seq, openFile }`；文档原文：**"entries without content return null"** | 可以做一个**只在"记忆相关答案"那一轮出现**的动作，其它轮次渲染为 null → 天然零噪声。这是"对话→面板"的最佳落点 |
| `ctx.sidebarRight` 导航控制器 | `openTab(kind, { params, paneId?, replaceTab?, preferNewPane?, revealIfOpened? })`；`params` 以 `tab.navigation.params` 到达正文 | 面板可以被**带参打开**（`{ view: 'b' }` 直达回收站），这是互跳的技术前提 |

### 1.3 ⚠ 插槽机制**无法**承载的预期（必须显式标注）

| # | 设计预期 | 核验结论 | 替代方案（本次采用） |
| --- | --- | --- | --- |
| **X-1** | 「面板里看某条记忆的来源，**跳回产生它的那段对话并高亮那一轮**」 | **没有公开面**。会话内的"滚到某轮"是 `ui-chat` 内部 `ChatView` 的命令式句柄（`scrollToTurn` / `activateTurn`），未作为服务/插槽暴露；`ISession.loadThrough(seq)` 只能保证**该轮被加载进窗口**，不保证视图滚动或高亮；也没有任何"高亮某轮"的公开能力 | **分级降级**：①**默认且唯一保证**＝来源区**内联摘录**（会话名 + 轮次 + 时间 + 触发原因 + 原文片段），零依赖、可断言；②**条件化**：只有当实现方能确认"选中来源会话 + 加载到该轮"两件事都成立时，才渲染「在对话中定位」按钮。**禁止**渲染点了没反应的按钮（§5.3 有硬约束） |
| **X-2** | 「角标显示本次会话新增数」 | **可算但不确定好看**：`sidebar.footer.action` 是 root 作用域、**宿主不注入 sessionId**，入口需自己派生"当前会话"；且 `wide=false`（56px 轨）时**没有位置放数字**（同排还有插件图标与 Settings）。详见 §4 | 推荐不显示数字；若拍板要显示，只在 `wide=true` 显示（§4.4 给了口径与前提） |
| **X-3** | 「无会话时也能浏览记忆（用户级记忆与目录无关）」 | **不可行且不该做**：右侧栏按会话 id 存状态，hero 屏右侧什么都没有；要绕过去只能用 `main` 键控整页做**第二套渲染面** | 明确定为**降级态 D-0**：无会话时入口不打开面板，给一条可解释提示（§7.2）。第二渲染面列为**不做**（PB-9） |

> 这三条是本任务里最有价值的发现：**X-1 与 X-3 会直接改变"互跳"和"无会话"两处的验收口径**，不能让实现方按"反正能做"去写。

## 2. 决策 E-1：入口位置 = `sidebar.footer.action`

### 2.1 结论

**采纳 team-lead 的倾向，推荐单一主入口挂在 `sidebar.footer.action`**（与既有插件面板同位），并追加两条 team-lead 没写、但必须有的约束：

- **E-1a**：入口是 **root 作用域常驻**——**不随会话出现/消失**。记忆是跨会话资产，"有会话才能看记忆"在语义上是错的。
- **E-1b**：**不设第二个图形入口**。`conversation.session.header.actions` 不放记忆按钮（该位已有 4 个占用者）。对话侧的"跳到面板"用 §5.1 的上下文动作实现，它是**按需出现**的，不占常驻 chrome。

### 2.2 为什么是它（四条依据，按权重排序）

1. **唯一"永远在"的可点区位**。`sidebar.footer.action` 是 root 作用域，无会话时也在；`conversation.session.header.actions` 无会话就整条头部都不渲染。记忆入口若随会话消失，用户会以为"记忆是会话局部的东西"——这与 D-1/D-6 的"记忆属于用户、跨会话沉淀"直接冲突。
2. **"浏览自己的档案"不属于"配置"**。设置页放的是开关、保留期、模型这类**参数**；记忆面板是**数据**。放进 `settings.section` 会让用户每次查记忆都先过一道"设置"的心智闸门，也会让设置导航越来越长。设置页**仍然要有一个入口**，但那是"记忆设置"（开关/保留期，属 P-1 范围），不是面板本身。
3. **与既有惯例一致，学习成本为零**。cordis-panel 已经在这个位，用户对"侧栏底部图标 = 打开一个面板"已经形成预期。新入口只是同排第二个图标。
4. **一次点击可达**。侧栏底部不经菜单、不经命令面板。对比之下，若藏在"命令面板/快捷键"里，就把低频但高敏感的操作变成了"需要先记住怎么打开"。

### 2.3 被否方案与否决理由（不留"都可以"）

| 方案 | 否决理由 |
| --- | --- |
| `conversation.session.header.actions` | ①无会话即消失（违反 E-1a）②该位已有 4 个占用者，第 5 个图标会被挤进溢出/窄屏让位区 ③头部动作的语义是"针对当前会话的操作"，而记忆是跨会话的 |
| `settings.section` | ①"设置"≠"数据浏览"，心智污染 ②三层导航（设置 → 分区 → 面板）才到清单，和"高频核对"直接冲突 ③§7.2 的关闭态、空态会被塞进设置页，页面角色混乱 |
| `sidebar.panellist`（全局面板图标，plugins/schedule 用的位） | 该位的 id 会**成为主栏的一个整页面板**（`main` 键控），意味着要做**第二套全页渲染**。违反"单一呈现形态"（§3.5），且与 §3 的右侧面板重复实现同一份清单 |
| 只做命令/快捷键 | 违反 D-7 的"面板属 MVP"意图：找不到入口的面板等于没有 |

## 3. 决策 E-2：打开形态 = 右侧面板页签（`sidebar.right.pane.tab`）

### 3.1 结论

| 项 | 结论 |
| --- | --- |
| 承载位 | `sidebar.right.pane.tab`，按**页签类型**注册一次，正文与标题分别注册 |
| 打开方式 | `ctx.sidebarRight.openTab('memory-panel', { params: { view: 'a' \| 'b' \| 'c', itemId? } })` |
| 页签条上的 chip 文案 | **「记忆」**（两个汉字，窄格也不被截断）；有角标时数字另行处理（§4） |
| 不是 | ❌ 独立整页（`main`）❌ 全屏 modal ❌ 抽屉 |
| 全屏 | **支持**，由宿主的两个面板控件提供（形态切换 / 折叠）；**<768px 打开时宿主自动全屏**，设计不自己造全屏 |
| 去重 | 同格内重复打开**聚焦既有页签**（宿主行为）；用户显式分栏时可出现在另一格——那是用户意图，不是 bug |

### 3.2 为什么适合"高频核对 + 长时间浏览"

| 场景特征 | 右侧页签为什么对 | modal / 整页为什么错 |
| --- | --- | --- |
| **要和对话对照**（"依据记忆"、冲突核对） | 面板与对话**同屏并存**，不需要来回切 | modal 会盖住对话，必须"关掉才能看对话"——恰好打断核对动作 |
| **一次可能看很久**（翻页、看版本链） | 它是页面的一列，滚动、选区、复制都正常 | modal 的滚动被锁在遮罩里，长内容会被压成小窗口 |
| **可能随时离开又回来** | 宿主把布局/页签身份存到会话级 localStorage，**刷新与切换会话都保留**；`keepMounted` 还能保留访问过的正文 | modal 一关就丢上下文 |
| **写入只能来自对话** | 面板常驻右侧时，用户仍能直接在输入框继续说话（PB-4：面板不是写入入口） | 整页会替换掉对话，用户要回到主栏才能写，路径变长 |

### 3.3 宽度与断点（**这是本次最重要的修订：容器断点，不是视口断点**）

> 上一版 `panel-memory.md` §8.7 的断点是**视口级**（≥1025 / 821–1024 / ≤820 / ≤520）。面板搬进右侧栏后，**视口 1440px 的屏幕上，面板本身可能只有 300–380px 宽**。因此原来的 820px 断点永远不会触发，面板会在 380px 里画出 236px 的左侧竖排页签 + 表格。**必须在容器内重定断点。**

| 档 | 面板可用宽度 | 内部页签形态 | 主清单适配 | 依据 |
| --- | --- | --- | --- | --- |
| **W1 宽** | ≥ 520px | **左竖排**（沿用 v1 的 rail 形态） | 完整：统计条一行、工具条一行四控件、条目三列 | 宿主右轨道最小 300px、最大约 66vw，W1 是"分栏后仍有富余"的常态 |
| **W2 中** | 380–519px | **顶排分段条**（三个等宽段：清单/回收站/变更） | 统计条两行；筛选 4 控件收进「筛选」按钮 + 已选条件回显；条目变"序号 + 内容"两列，操作按钮下沉 | 单页签阅读在 380px 仍舒适 |
| **W3 窄** | < 380px（折叠轨/分栏 20–80% 的窄侧） | 顶排分段条，段内只留**符号 + 数字**（`A 6` / `B 1` / `C 4`） | 统计条拆两行且省略公式行；筛选折叠；条目单列；分页器只留"上一页/下一页" | 宿主允许 300px 起，必须能用到 300px 不横向滚动 |

**硬要求**：实现必须用**容器查询**（或等价的"按面板实际宽度分档"机制），**不得**沿用 `@media (max-width: …)` 判断面板形态。这是一条会被"照抄上一版 CSS"踩中的坑，所以写成契约（PE-07）。

### 3.4 全屏与分栏的取舍

- **全屏**：支持，但**不设"记忆专用全屏按钮"**——用宿主在页签条右端已有的两个面板控件（形态切换、折叠）。理由：自造按钮会出现两个全屏控件，且宿主的全屏路径已处理窄屏、Windows 标题栏、焦点等边界。
- **全屏不重挂载**：宿主"普通/全屏共用同一棵内容树"，所以**切换全屏不得丢失**：当前页签、筛选条件、页码、搜索词、已展开的折叠小节。这一条要写进用例（PE-08）。
- **分栏**：允许两个水平格，记忆面板可占其中一格（最小 300px）。**设计不为分栏做任何额外形态**，W3 档就是它的答案。

### 3.5 为什么不做第二呈现形态（明确的范围线）

一套数据、两套渲染面（右侧页签 + `main` 整页）= 两份布局、两份断点、两份无障碍，而收益只是"无会话时也能看"。**明确不做**，记为 PB-9，并在 §7.2 给出无会话时的可解释提示。

## 4. 决策 EB-1：`sidebar.footer.action` 的角标显示什么

> **状态：✅ 已拍板 = 方案 A（不显示角标）。**
> **裁定来源**：team-lead，2026-11-01，采纳本文的独立评估结论；原倾向"本次会话新增数"由 team-lead 自行收回。
> **裁定理由（team-lead 原话要点）**：「记忆没有'待处理'概念（OQ-11=A 全自动写入，不存在待确认队列），角标语义本应是'有事等你'，而记忆没有这种事。我原先把'新增数'往角标上放，是把统计信息错放到了通知位。」以及：它会把 D-5 Q1 的"有限出声、有预算、可关闭"退化成"永久出声"，属业务规则层倒退，不是视觉偏好。
> **⚠ 保留说明**：下方 §4.3 的三条硬障碍**刻意保留不删**。若未来要加角标，必须先跨过这三条，别重新踩一遍。
> 实现口径：**PE-19 = 不显示任何角标**（数字与点都不显示）；PE-20 因此变为"若未来启用才需要进 DECISIONS"。

下面是当时的独立评估与推荐，作为裁定依据留档。

### 4.1 三个候选与我的评估

| 候选 | 语义是否成立 | 可维护性 | 噪声 | 我的判断 |
| --- | --- | --- | --- | --- |
| **A 不显示** | 成立：入口是"去某个地方"，不是"有事等你" | 最好（零计算、零订阅） | 零 | ✅ **推荐** |
| **B 记忆总条数** | **不成立**：角标语义是"未读/待处理"，条数是静态属性。数字会随写入单调增长，涨了也不代表要做任何事 | 中（要订阅全库计数，还要与面板首行 N 同源，否则两处数字打架） | 中：常驻一个不断变大的数字，用户会解读成"欠了什么" | ❌ 不推荐 |
| **C 本次会话新增数** | 半成立：它确实"新"，但没有对应动作。用户看到 3 之后能做什么？唯一动作是"进面板看看"，与不带数字的点击结果完全相同 | **差**：见 4.3 三条硬障碍 | **高**：与 G-5「静默是默认，出声必须付费」直接冲突 | ❌ **明确反对** |

### 4.2 我为什么反对 C（"本次会话新增数"）

1. **它与 D-5 Q1 抢同一件事，但把"瞬时的轻声提示"变成了"常驻的数字"**。Q1 的裁定是：每会话**前 3 次**自动写入各给**一行**提示，第 4 次起**完全静默**，用户还能说"以后别提示写入"关掉。这个设计的前提是**提示会消失**、**有预算**、**可关闭**。角标是常驻的、无预算的、不随静默设置关闭的——它会把 Q1 精心设计的"有限出声"变成"永久出声"。**这是一次业务规则层面的倒退，不是视觉偏好问题。**
2. **它制造一个用户无法归因的数字**。用户看到"记忆 3"，问的是"3 什么？"——不是 3 条记忆（总条数可能是 6），不是 3 条待办（没有待办），而是"本会话新增"。这个词在界面上没有位置展开解释（56px 轨里更不可能）。凡是需要 tooltip 才能看懂的数字角标，都是设计失败的角标。
3. **它把两处通道的可信度绑在一起**。若角标与对话侧提示不同源，用户会看到"提示说记了 1 条，角标说 2"；若同源，则面板/对话/角标三处都要对同一个"本会话"定义负责（会话怎么算？刷新页面算新会话吗？`/clear` 呢？切到别的会话再切回来呢？）。**每多一个展示位，就多一组会被测出不一致的断言。**

### 4.3 若用户仍要 C：三条硬障碍必须先解决（我不假设它们能解决）

| # | 障碍 | 事实 |
| --- | --- | --- |
| C-1 | **宿主不把会话身份给这个位** | `sidebar.footer.action` 是 `root` 作用域，ownerProps 只有 `{ wide }`。入口必须自己派生"当前会话"（cordis 的做法是 `useSessions` 里找 `retainedBy.mainView > 0` 的那个）。hero 屏/全局面板打开时派生结果为 `undefined` → 角标要么消失要么显示 0，**两种情况都是用户可观察的抖动** |
| C-2 | **折叠轨放不下数字** | `wide=false` 是 56px 图标轨，同排已有插件图标与 Settings。"本次会话新增"若达到两位数（一次长会话很容易），数字要么被截断，要么挤掉图标，要么退化成点——三者都不是"显示新增数" |
| C-3 | **口径要靠来源引用反查，没有现成字段** | 记忆条目有"来源引用"（会话 + 轮次 + 时间），所以"本会话新增"= 按来源会话过滤计数，**可算**；但必须定义"本会话"的边界（会话开始时间？页面加载时间？面板上次打开时间？），并且这个口径要与 D-5 Q1 的"前 3 次"提示**用同一个定义**，否则两处会不一致。**这条口径本身就是一次需要产品确认的裁定** |

### 4.4 推荐结论（已拍板）与「若未来恢复 C」的最小规范（留档）

**已拍板：方案 A（不显示角标）。**
理由一句话：**记忆没有"待处理"概念（OQ-11=A 全自动写入，不存在待确认队列），因此没有任何事件值得一个常驻角标；而"新增数"是统计信息，属于面板首行的职责，不属于入口。**

**（留档）若未来恢复「方案 C」，则按下表实现；在此之前任何角标均为缺陷（PE-19）：**

| 项 | 最小规范 |
| --- | --- |
| 显示条件 | **仅 `wide === true` 时**显示数字；`wide === false`（56px 轨）**只允许显示点**（≤ 4px 圆点，无数字） |
| 口径 | 新增数 = `count(条目.来源引用.会话 == 当前会话 且 条目.状态 ∈ {生效, 已修正})`；"当前会话"= 入口派生的、主栏正在显示的那个会话；派生不出来时不显示角标（显示 0 或消失都不对，**不显示**） |
| 与对话一致性 | 必须与 D-5 Q1 的"前 3 次"使用**同一个"本会话"定义**；测试要能同时读到两处（§5.4 的 E2C-4） |
| 与面板一致性 | 角标的数字**不要求**等于面板首行 N（N 是可见集总数，口径不同）——因此**必须**在 `aria-label` 里说清"本会话新增 k 条"，绝不能让数字看起来像"共 N 条" |
| 复位 | 会话结束即归零（无需用户操作）；**不提供"清零"** |
| 无障碍 | `aria-label` = 「记忆，本会话新增 k 条」；数字本身 `aria-hidden` 由 label 承担；不得只靠颜色 |

**风险提示（若未来启用角标）**：入口与 Settings 同处脚区、`wide` 会在 56px 与完整宽度之间来回切换，任何角标都必须验证**两种 wide 状态下的布局不抖动、不遮挡**——这一项我只能给规范，无法在真机确认（§13 U-4）。

## 5. 决策 E-3：双通道互跳（S-1 / S-2 的落地）

### 5.1 对话 → 面板：**不用常驻按钮，用"只在相关那一轮出现"的上下文动作**

| 项 | 结论 |
| --- | --- |
| 承载位 | `conversation.chat.turnTail`（list / session，ownerProps `{ turn, seq }`） |
| 出现条件 | **仅当这一轮的助手输出里包含"记忆清单/回收站/变更记录"的应答时**出现；其它轮次**必须返回 null**（宿主文档明确支持"entries without content return null"） |
| 文案（逐字） | `在面板中打开 · 共 6 条` / `在面板中打开 · 回收站 1 条` / `在面板中打开 · 变更记录 4 个版本` |
| 点击行为 | `openTab('memory-panel', { params: { view: 'a' \| 'b' \| 'c' } })`；若面板已开，**聚焦既有页签**并切到该视图（不得新开第二个记忆页签） |
| 为什么不用"清单末尾附一行指令" | 指令要靠用户**再打一遍**，而按钮是零成本的；且指令在长清单末尾容易被滚走 |
| 为什么不做常驻的"记忆"按钮在会话头部 | 见 E-1b：已有 4 个占用者，且常驻按钮会与侧栏入口重复 |

**对话指令（补充路径，必须实现最少这一条）**：用户直接说「打开记忆面板」也能进。词表新增 4 行见 §11.3。

### 5.2 面板 → 对话：**默认给"来源摘录"，条件化给"定位"**（因为 X-1）

面板条目详情的「来源」区**必须**包含（这是 S-1/AC-11 的可见面，不依赖跳转能力）：

```
来源  2026-10-30 15:12 · 会话「记忆面板入口设计」第 12 轮
      触发原因：你纠正测试命令时（你纠正过的）
      摘录：「测试命令是 pnpm test，不是 jest」
```

| 能力 | 是否必须 | 条件 |
| --- | --- | --- |
| 来源摘录（会话名 + 轮次 + 时间 + 触发原因 + 原文片段） | **必须** | 无 |
| 复制来源引用 | **必须** | 无（等价于对话通道的"第 N 条来源"回执，可复述性 A-2） |
| 「在对话中定位」按钮 | **条件化** | **只有**实现方能确认下面两件事都成立才渲染：①能把来源会话带到前台；②该轮次能被加载并在视图中被明确指认（滚动或高亮二选一）。缺任一件 → **不渲染按钮**，只保留摘录 |
| 渲染了按钮却点了没反应 / 只切会话不指认 | **禁止**，视为缺陷 | — |

> 这条约束是为了防一个很常见的失败：设计稿上画了一个漂亮的"跳回对话"按钮，实现方只能用"切到那个会话"凑数，用户点了发现"不知道让我看哪一句"。**宁可不给按钮，也不给假按钮。**

### 5.3 可断言的验收点（test-engineer 可直接转用例）

| ID | 步骤 | 断言（可观察） |
| --- | --- | --- |
| **E2C-1** | 对话问「你记得我什么」→ 点该轮下方的 `在面板中打开 · 共 N 条` | 面板页签 A 打开；**面板首行 N / a / b / c 与对话清单首行的四个数字逐项相等** |
| **E2C-2** | 对话说「看回收站」→ 点该轮的 `在面板中打开 · 回收站 k 条` | 面板**直接落在页签 B**（不是先落 A 再切）；条数 = k |
| **E2C-3** | 一轮**与记忆无关**的普通回答 | 该轮**没有**任何记忆相关动作（`turnTail` 贡献为 null）；全页不出现"记忆"按钮 |
| **E2C-4** |（仅当 EB-1 采纳 C）会话内发生 3 次自动写入 | 侧栏入口的 `aria-label` 里的"本会话新增 3 条"与对话侧 3 行轻量提示的次数**一致**；第 4 次写入后对话静默但角标变 4 —— **该差异必须写进 DECISIONS**（这是 C 的已知代价） |
| **C2E-1** | 面板打开某条生效条目的详情 | 来源区**必然**含：会话名、轮次、时间、触发原因、摘录；这些字段与对话「第 N 条来源」的回执**逐项一致** |
| **C2E-2** | 面板编辑第 3 条内容 → 立刻在对话问同话题 | 只返回新内容（S1-1 继承）；面板首行 a/b 随之变化（旧转已修正、新为生效） |
| **C2E-3** | 面板普通删除 → 对话说「你记得我什么」 | 清单不含该条、N 减 1；面板页签 B 出现该条（S1-2 继承） |
| **C2E-4** | 面板已开时，在对话输入「打开记忆面板 → 回收站」 | 面板**切到页签 B**；记忆页签**总数仍为 1**（不得新开） |
| **C2E-5** | 点「在对话中定位」（仅当该按钮被渲染） | 视图**明确指认出**来源那一轮（滚动到位或有可见高亮），且不是"静默切了会话" |

### 5.4 S-2 语义等价在入口层的追加约束

- 入口只是"打开同一个面板"的两种走法，**不得**产生两条不同的默认视图：侧栏入口默认 = 页签 A；对话动作按其文案指到 A/B/C。**其余状态（筛选、页码、搜索）不通过入口传递**——从入口进永远是"干净的首屏"，避免"点进去发现还带着上次的筛选，以为记忆丢了"。
- 反之，**面板内已开的会话内状态不因再次点击入口而重置**（去重聚焦，不重开）。

## 6. 决策 E-4：降级路径（S-4 的落地）

### 6.1 结论

**图形入口是增强，不是前提。** 记忆的全部业务能力在对话通道上必须**完整存在**，且**判定口径不变**（S-5）。图形入口缺失时，用户不应观察到任何"能力减少"，只应观察到"少了一个按钮"。

### 6.2 三种情形与用户可观察的表现

| 情形 | 用户看到什么 | 必须不出现什么 |
| --- | --- | --- |
| **D-1 纯终端 / 无 GUI / 未安装前端插件** | 侧栏底部**没有**记忆图标；对话里说「你记得我什么」「打开记忆面板」等全部照常工作（后者在无 GUI 时回应"这个环境没有面板，我直接把清单打给你"） | ❌ 不得出现"面板不可用，所以不能查看记忆" ❌ 不得出现任何依赖面板的独占能力 |
| **D-2 面板打开失败**（右侧栏不可用 / 会话已卸载 / 无会话） | 入口点击后给**一条就地提示**（文案见 §7.2 D-0 / D-2）；对话侧行为完全不变 | ❌ 死按钮（点了毫无反馈）❌ 把错误抛到控制台却什么都不显示 |
| **D-3 面板渲染失败**（前端插件异常） | 面板体内给**错误态 + 重试**：`记忆暂时读不到（超时），这次没法给你清单。`（沿用 DC-16 / DC-31，**不得套用空态文案**） | ❌ 把"请改用对话"写成唯一出路（那是把面板当唯一路径，违反 S-4）；**允许**并列一句"也可以在对话里查「你记得我什么」"作为**补充** |

### 6.3 为什么"面板不是写入入口"在这里又赢一次

`PB-4`（无写入入口）在本任务里第二次产生收益：**面板整个挂掉，写入链路毫发无伤**。因此"入口坏了"的最坏后果只是"少一个查看窗口"，不是"记忆不能用"。这条要写进交接（§12）。

## 7. 决策 E-5：记忆关闭 / 无会话 / 其余入口状态

### 7.1 记忆功能被关闭（OQ-1 支持一键关闭）

**结论：保留入口，不隐藏；降饱和 + 就地说明；点击不打开面板。**

| 处理 | 做法 | 为什么 |
| --- | --- | --- |
| 图标 | 保留同一图形，**去饱和**（`opacity` 降但保持 ≥3:1 对比，见 §9） | 完全隐藏会让用户以为"功能被移除"或"我的记忆被删了"——记忆是隐私敏感能力，静默消失是最坏的反馈 |
| 就地说明 | 入口下方（`wide` 时）或 tooltip（rail 时）显示 `记忆已关闭` | 状态可发现，无需点进去 |
| 点击 | **不打开面板**，给一条提示：`记忆已关闭。在对话里说「开启记忆」可以打开。` | 打开一个"什么都没有"的页，是把"看不到"包装成"看了" |
| 提供一键开启 | **不做**（与 `panel-memory.md` §11.3 的 P-1 一致） | 开关属 harness 配置；两处开关会打架 |
| 面板关闭态页（`panel-memory.md` §5.4 状态 9） | **保留**，用于"面板已经开着，期间记忆被关闭"的情况 | 那条路径必须给"半残清单"以明确替代，不能留在旧数据上 |

**被否方案**：①隐藏入口（见上）②置灰不可点且无文字（用户不知道原因）③点击后打开关闭态空页（多一次导航换零信息）。

### 7.2 无会话（hero 屏 / 全局面板占满主栏）→ 降级态 **D-0**

**结论：入口仍渲染；点击不打开面板，给一条可解释提示。**

| 项 | 内容 |
| --- | --- |
| 判定 | 宿主 `ctx.sidebarRight.mounted` 为 `undefined`（无前台会话）时即为 D-0 |
| 文案（逐字） | `记忆面板跟随会话显示。先新建或进入一个会话。` |
| 为什么不做 | 见 §3.5：第二渲染面（`main` 整页）成本过高、且会引出两套断点与两套无障碍 |
| 别写什么 | ❌ 不要写"面板不可用"（像故障）❌ 不要写"请稍后再试"（不是时间问题） |

### 7.3 入口的 8 类状态（逐一有稿，原型可复现）

| # | 状态 | 入口表现 | 依据 |
| --- | --- | --- | --- |
| 1 | 正常（有会话、记忆开启） | 图标 + 「记忆」，可点 | — |
| 2 | 悬停 / 聚焦 | hover 底色；**3px 焦点环，对比 ≥3:1** | PC-38 继承 |
| 3 | 面板已打开 | 入口保持"已选中"观感（与 cordis 的 `data-active` 同构），**再次点击 = 聚焦，不新开** | 去重 |
| 4 | 记忆已关闭 | 降饱和 + `记忆已关闭`，点击给提示 | §7.1 |
| 5 | 无会话（D-0） | 正常外观，点击给提示 | §7.2 |
| 6 | 折叠轨（`wide=false`） | **只有 18px 图标**（同 cordis），无文字、无数字；tooltip/aria-label 承担全部语义 | 宿主事实 |
| 7 | 面板渲染失败 | 入口不受影响；面板体内错误态 + 重试 | §6.2 D-3 |
| 8 | 角标（EB-1 已拍板） | **不显示**（数字与点都不显示）；§4.3 三条硬障碍留档，供未来启用时先跨过 | §4 |

> 权限不足：D-1（本机单用户）下不存在，故无此态，与 `panel-memory.md` §5.4 一致。

## 8. 视觉与可访问性规范（只定义入口新增部分）

### 8.1 入口按钮规格

| 项 | `wide = true` | `wide = false`（56px 轨） |
| --- | --- | --- |

### 8.3 与既有 occupant 的共存（**D-9 已裁定为纵向叠放**）

> **D-9（team-lead，依据 fullstack-engineer 实测）**：本节原「同排、236px 下不换行」的假设被实测推翻，已改为**纵向叠放**。证据见 `docs/tech-design.md` §10.1 F-8/F-12 与 §10.2 U-4。

- 入口在 `sidebar.footer.action` 中与 cordis 插件入口、Settings **纵向叠放**，各占整行；记忆入口 `order:-1`，位于插件入口**之上**。
- **根因**：cordis 入口自身为 `flex:none; width:calc(100% + 4px)`，宽态已独占整行。再放入任何 ≥1px 的同排项，行内合计即超可用宽，入口被 `overflow:hidden` 裁切（实测 280px 下记忆入口右溢 **+244px**，几乎完全不可见）。**同排在本宿主几何下不可行，是几何结论而非偏好。**
- **侧栏宽度事实**：宿主为 **264–420px，默认 280px**（不是 236px）。所有宽度相关断言按 264/280/420 三档写。
- **折叠轨**：轨内可用宽 **36px**，故「命中区 ≥44×44」**仅适用宽态**；折叠轨沿用宿主既有的 **36×36**（与 Settings、cordis 一致，比邻居大反而更差）。**macOS 桌面折叠时整列隐藏、无轨道**，该形态只与 Web GUI / Windows 有关。
- **不改宿主 CSS**：只给本入口自身 class 加规则 + 对 `.footerActions` 一条容器规则；若宿主升级改了类名，**入口视觉退化但功能不坏**（刻意的降级设计）。
- **不模仿** cordis 的"角标计数 = 在跑+待确认"语义：那个数字是"有事在等你"，记忆没有对应物（这正是 §4 反对 C 的同一个理由）。
