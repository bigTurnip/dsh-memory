## D-3 取消「四种类型」分类，**保留分层**（关键变更）

- **结论**：取消语义记忆的 `conclusion / correction / preference / lesson` 四分类。**不再有「类型」字段，不做类型标签、不做类型筛选。**
  但**保留分层**：`episodic`（情景）/ `semantic`（语义）/ `procedural`（程序）。
- **修正 PRD 三处**：
  - §3.1 R-3.1.3（原「新增条目必须落在四类之一」）**作废**。
  - §3.7 条目字段中的「类型」字段**删除**；「分层」字段保留为唯一的结构性归类。
  - §8「与 `kb_remember` 四分类对齐」**作废**——记忆条目与知识库资料是两套数据，不再要求类型枚举对齐。
- **连带影响（必须处理，不得遗漏）**：原「`correction` 类型」承担了「用户纠错」的识别职责。类型取消后，纠错改为**不依赖类型标签的通用机制**：
  1. 识别依据：用户在**同一次对话内**对既有记忆的显式否定（「不对，是 X 不是 Y」「以后改用 X」）。
  2. 处理结果：旧条目 `status` 转为 `已修正`，新条目生效（PRD §3.3 冲突策略 A 不变）。
  3. 用户可观察：列表中出现「已修正」状态标识，检索只返回新条目。
  4. 强约束不变：纠错**当次会话内立即生效**。
- **影响 MVP 展示**：MVP 实际只有两层层级可展示——**语义（Must）** 与 **情景（Should S1）**。程序记忆不纳入 MVP，不出现空分组。
- **来源**：用户原话「记忆不需要分类」，经追问收敛为「只取消四种类型，保留分层」。

## D-7 【范围变更】记忆管理面板纳入 MVP，推翻 OQ-7=A

- **结论**：**推翻 OQ-7=A**。记忆管理**不再是「仅对话指令」**，而是**对话指令 + 图形面板并存**（等价于原 OQ-7=C）。面板属于 **MVP 范围**，不是 Should。

- **连带修改（必须同步，不得遗漏）**：

| # | 受影响项 | 变更 |

  - **S-5 判定口径不变**：D-4 的 C-2（计数准确性）、C-3（V-A 专指）在面板形态下**依然有效**。

## D-8 契约矛盾裁定（X-1~X-9，由 test-engineer 发现，team-lead 裁定）

来源：test-engineer 交付 task-6 时发现 9 条契约矛盾（test-plan.md §12），全部未自行选边。以下裁定为**唯一生效口径**，下游文档与本裁定冲突时以本条为准。

### 高危 4 条

**X-1 「忘掉」的档位**：「忘掉」歧义源于触发语表同时把它映射到隐私硬删与批量软删。**裁定：按指代对象区分**——
- 带具体指代的单条（「忘掉第 N 条」）→ **普通软删**（与 F5 默认档一致，可恢复）；
- 「忘掉关于 X 的全部记忆」（批量，F6）→ **普通软删 + 预览后执行**；
- **只有**「彻底删除 / 永久删除 / 不要留副本」等**显式不可逆措辞**才触发隐私硬删。
- 理由：S-2 要求默认档位统一为软删；「忘掉」是日常用词，若默认硬删，误触代价不可逆，与 OQ-5=C「隐私删除需二次确认」的保护意图相悖。design-agent-memory.md §5.9 触发语表中「删除（隐私）：…忘掉…」一行**作废**，由本条取代。

**X-2 DC-10 计数口径与筛选的关系**：**裁定：DC-10 的 N 在筛选态下 = 筛选后集合的计数**。DC-10 原文补限定词「（未筛选时 N = 全量 V-A 可见集；有筛选时 N = 筛选后集合，且首行必须显示当前筛选条件）」。PC-12/§5.8 的写法正确，按其执行。DC-10 原句「a+b+c = N = 实际 V-A 可见条目数」理解为**默认无筛选态**的表述，不构成对筛选态的否定。
- 理由：D-4 C-2 已裁定「不多不少」约束计数准确性；筛选后显示全量数会让用户误判当前视图内容，违背计数准确的本意。

**X-3 已过期折叠阈值的作用域**：**裁定：两通道统一为「V-A 全清单已过期合计 > 5 条才折叠」**（对话与面板同一口径）。panel-memory.md §3.5-5「单层内超过 5 条」**作废**，改为全清单口径。
- 理由：S-5 判定口径不变是硬约束；「2 层各 4 条」在两通道得出相反结论直接违反 S-5。全清单口径实现也更简单（一个计数器）。

**X-4 回收站「保留 30 天」文案**：**裁定：文案必须与实际行为一致，禁止为未实现的行为背书**。拆解——
- MVP 若实现 30 天清理：文案「回收站条目保留 30 天后彻底删除」；
- MVP 若实现为不过期（D-5 Q2 允许）：文案只能写「可恢复」，**不得**出现任何具体天数承诺；PC-23 的「30 天」字样按实现实际行为取用。
- **推荐 MVP 实现 30 天清理**（与 D-5 Q2 主裁定一致），工程师按推荐实现则 PC-23 原文有效。
- 理由：向用户宣称一条不存在的承诺，比没有承诺更糟——它会让用户基于错误预期做删除决策。

### 中危 3 条

**X-5 「角标」一词的两个对象**：**裁定：test-engineer 的解读正确**。PE-05/PE-19 约束的是**侧栏入口与右侧栏 pane chip**（不显示任何数字/点）；PC-11 的「页签角标」指**面板内部 A/B/C 页签的计数**（允许且应当存在，受 PC-11 同源约束）。两者不冲突，是两份文档用词撞车。
- 附注：panel-memory.md 中「角标」一词建议改为「页签计数」以免再撞（改词不改语义，属编辑性修订，不构成契约变更）。

**X-6 「别记」移除的档位**：**裁定：走软删**，但**必须在回收站条目上标注「因用户要求不保留」**，且用户在回收站看到该条目时的展示文案注明其被移除的原因。不触发硬删（硬删需显式不可逆措辞，见 X-1）。
- 理由：N-2 的用户意图是"别留"，软删已满足"从 V-A 与检索消失"；硬删是不可逆操作，不应由「别记」这种日常语触发。回收站可见原文不构成违背用户意图——回收站本身就是"用户主动管理已删内容"的地方，用户可以随时从那里彻底删除。

**X-7 四要素/五要素**：**裁定：统一为五要素**（序号、分层、作用域、来源时间、来源事件短语），DC-32 的列举为准。§7.3-2 的「四要素」为笔误，按 DC-32 更正。编辑性修订，无实质影响。

**X-8 DC-12 表格禁则的适用范围**：**裁定：DC-12 仅约束对话通道的清单输出**。面板（PC 系列）不受 DC-12 约束，panel-memory.md 明确规范了面板表格的 caption/th 规则，按其执行。test-engineer 的解读正确。

**X-9 AC-5 的「数据库密码」示例**：**裁定：AC-5 的验收场景应使用非凭据目标**。PRD AC-5 When 句的「数据库密码」例子不当（凭据本就不写入，不存在删除路径），测试一律用非凭据目标构造 AC-5 场景；密码场景只用于 AC-7（不得写入）验证。PRD AC-5 的 When 例子**作废**，替换为非凭据示例（如「彻底删掉我刚才说的家里 WiFi 名」——**注意必须用 X-1 的显式不可逆措辞**，因为 AC-5 验的是隐私硬删路径；用「忘掉」会落到软删档，验不到硬删）。AC-5 的验收语义（隐私删除后不可恢复、不可见、不泄露）不变。

## D-11 测试侧实测发现的 4 项问题裁定（N-1 ~ N-4）

来源：test-engineer 在执行 task-7 时独立实测发现，报 team-lead 裁定。**均已由 team-lead 复核源码确认为事实**，非测试误报。

### N-1 关闭态下 `memory_list` 仍输出清单 —— **判缺陷**

- **事实**：`enabled=0` 时 `memory_write` → not-salient、`memory_search` → degraded:error，但 `memory_list` **仍正常输出清单**（实测「记忆清单 ｜ 共 1 条」）。
- **契约要求**：设计 §5.7 / F3-c / D-3 均明确，关闭态应答为 `记忆已关闭，我现在没有可查的记忆。说「开启记忆」可以打开。`
- **裁定**：**实现缺陷，须修**。理由：关闭态下"能看到记忆"与"记忆已关闭"直接矛盾，用户无法判断功能状态；且这是隐私语义问题——用户关闭记忆后仍能列出内容，违背 OQ-1 关闭的可预期效果。
- **修复要求**：`memory_list` 与 `memory_manage`（查询类）在 `enabled=false` 时必须返回统一的关闭态文案，不得输出条目。
- **影响用例**：TC-AC9-03。

### N-2 降级检索不写审计 —— **判缺陷**

- **事实**：`faults.retrieveSlowMs=300` 得到 `degraded:'timeout'` 后，`queryAudit()` 返回 `[]`；关闭态检索同样无留痕。根因是 `service.retrieve()` 的三个提前 return 分支（关闭 / error / timeout）都在 `dao.audit` 之前返回。
- **契约要求**：PRD §6.3 O-2「每次检索留痕：查询意图、命中条目 ID、耗时、是否被实际采用」；AC-9 And「该次失败被记录到可观测指标」。
- **裁定**：**实现缺陷，须修**。理由：AC-9 的验收本质是"失败可被观测"，若失败不留痕，等于失败无法被发现——这比失败本身更危险。
- **修复要求**：三个降级分支都要写审计（`op='retrieve'`，`outcome` 记 `timeout`/`error`/`disabled`），`meta` 仍不含查询原文。
- **影响用例**：AC-9 第二条此前**无法判定**，修复后方可判定。

### N-3 开关指令无执行通道 —— **判缺陷（实现缺功能）**

- **事实**：`开启记忆/关闭记忆/以后别提示写入` 在 4 个工具与 HTTP 路由里**都不存在**；只有 `MemoryService.setEnabled` 进程内方法。
- **契约要求**：D-2（OQ-1=A「默认开启，**可一键关闭**」）、设计 §5.7 关闭态应答含「说『开启记忆』可以打开」。
- **裁定**：**判缺陷，不是缺观测面**。理由：OQ-1 明确要求"可一键关闭"，且设计文案已经向用户承诺了「说『开启记忆』可以打开」——承诺了却做不到，属实现缺功能。若只当观测面缺失处理，等于默认这个承诺可以不兑现。
- **修复要求**：补一个开关通道（建议 `memory_manage` 增加 `action: 'enable'|'disable'`，或独立 `memory_toggle` 工具）。若工程师认为该功能应移出 MVP，**必须回到 DECISIONS 讨论改 OQ-1**，不得静默缺失。
- **影响用例**：TC-AC9-03 的前置条件此前只能靠测试进程内直接调 service，修复后可经对话完成。

### N-4 V-A 首行缺工作目录名 —— **判缺陷**

- **事实**：实测输出 `记忆清单 ｜ 共 4 条（…）`；`formatCountLine()` 只拼 `记忆清单 ｜ 共 N 条`，无项目名。
- **契约要求**：DC-04 / §5.8b 要求 `记忆清单 ｜ 项目 <目录名> ｜ 共 N 条`，并明确「首行项目名是 AC-8 的判定锚点」。
- **裁定**：**判缺陷，须修**。理由：AC-8（跨项目不串味）在无界面时需要可被用户与测试同时读取的锚点；缺了它，用户无法确认当前看到的是哪个项目的记忆，AC-8 的可判定性也被削弱。
- **修复要求**：`formatCountLine` 增加 `projectName` 参数；有 projectKey 时输出 `记忆清单 ｜ 项目 <name> ｜ 共 N 条`，无 projectKey（无会话）时输出明确的无项目态文案。
- **影响用例**：TC-AC6-01、TC-AC8-01。

### 附：AC-10「写入抽取为异步」的口径确认

- **事实**：实现为同步落库，D-4 未覆盖此点。
- **裁定**：**按"不阻塞的可观察等价物"断言**，不要求异步管线存在。具体断言：①写入耗时 P95 < 50ms；②写入后立即可被检索命中；③写入不阻塞同轮对话响应。
- **理由**：AC-10 原文意图是"写入不拖慢对话"，异步只是达成手段之一。在本地 SQLite 场景下同步写入若足够快，等价满足用户可观察目标。**但必须记录该偏离**，不得让后续读者以为实现了异步管线。

### 附：验证脚本退出码假阳性 —— **执行纪律，非代码缺陷**

- **事实**：`recall.mjs` 与 `u4-entry-metrics.mjs` **无 `process.exit`**，无论结果如何都 exit 0。故 `verify-all` 的「H-1 PASS / U-4 PASS」是**退出码假阳性**，不能作为通过证据。
- **裁定**：**记为实现缺陷（自测脚本），须修**——脚本应设退出码，否则 verify-all 的汇总结论不可信。
- **在修复前的执行纪律**：测试侧判定 H-1 / U-4 两段时**必须读输出内容**（如 43/60、47/48），不得看退出码。test-engineer 已在计划中写入该纪律。

### 附：真实 GUI 层当前不可执行

- **事实**：`~/.dsh/profiles/{desktop,web,headless}` 均无 `@clinexin/dsh-memory`（仅 `@clinexin/dsh-kb`）；`/api/memory/health` 返回 401。
- **裁定**：**L4 面板真机 / L5 双通道互跳 / 入口真机几何 整体判「未验证」**，不计入通过。解锁条件：将包 link 进 profile 并重启 GUI。测试计划须明确列出该未验证块与解锁步骤。

### 追加（D-11 N-4 落地时发现的接口冲突）：V-A 首行的权威格式

fullstack-engineer 按 N-4 实现「无项目上下文」显式态后，发现与测试侧解析器 `src/test/assert/parse-list.ts:159` 的 `RE_LIST_HEAD` 冲突（该正则只认「省略项目段」或「｜ 项目 <name> ｜」）。**裁定：改解析器，实现不动。**

理由：把实现改成「无项目时省略该段」会让无项目态与 N-4 修复前的旧输出**逐字相同**，等于 AC-8 的锚点在最需要它的场景（无项目上下文）下不可判定——正是 D-11 要消除的问题。

**V-A 首行权威格式（三态，互不相同、可被解析器区分）**：

| 状态 | 格式 |
| --- | --- |
| 有项目 | `记忆清单 ｜ 项目 <目录名> ｜ 共 N 条（生效 a / 已修正 b / 已过期 c）` |
| 有项目 + 筛选 | `记忆清单（<filterLabel>） ｜ 项目 <目录名> ｜ 共 N 条（…）` |
| 无项目上下文 | `记忆清单 ｜ 无项目上下文 ｜ 共 N 条（…）` |

- `<目录名>` 取 projectKey 的**末段目录名**，不输出全路径（避免啰嗦与目录结构泄露）。
- 恒等式 `a+b+c=N` 三态一致，不受项目段影响（DC-10 口径不变）。
- 解析器须把「无项目上下文」收为**显式分支**，而非当作旧格式省略段。

**测试侧注意**：若为兼容历史样例仍保留「省略段」的解析路径，应确保它**不会掩盖回归**——即实现若哪天退回无锚点格式，必须仍能被判定为缺陷（例如仅在显式 legacy 模式下接受省略段，或对该路径单独打标记）。

### 追加（N-1 落地时的范围澄清）：关闭态的可执行范围

工程师实现 N-1 时把 `memory_manage` 的**全部条目操作**都拦了（不只查询类），并问是否应允许关闭态删除。裁定：**维持，关闭态只放行 `enable`**。

| 可执行 | 说明 |
| --- | --- |
| ✅ `enable` | F3-c 文案承诺的出路，必须可达，否则「说『开启记忆』可以打开」成为不可兑现承诺 |
| ❌ `list` 及全部视图（V-A/V-B/V-C） | 关闭态不得输出任何条目 |
| ❌ `edit` / `delete` / `hard_delete` / `restore` / `batch_forget` | 这些 action 的回执都会回显条目正文，与 list 输出条目是同一个隐私矛盾 |

**不允许关闭态删除的三条理由**：
1. 关闭态文案承诺的出路只有「开启记忆」一条，允许删除需改文案承诺，属产品规则变更。
2. 关闭态下用户**看不见条目**，"看不见但能删"自相矛盾——删错后连回收站都查不到。
3. 正确路径为「开启 → 列表 → 删除 → 可再关闭」，多一步但每步可感知、可撤销。

**配套要求**：`disable` 的回执须让用户知道"现在起不再记录，且清单不可查"，与 F3-c 语义呼应。「以后别提示写入」是**持久设置**（存 `memory_settings`），跨会话生效；静音后 `memory_write` 仍正常执行，仅不出提示行。

## D-13 测试侧资产物理隔离（用户要求：测试代码不得污染开发测试代码）

### 隔离方案

| 侧 | 位置 | 归属 | 门禁 |

| **开发侧** | `src/test/` | fullstack-engineer | `npm run verify` → `src/test/verify-all.mjs`（**6 段，只跑自有脚本**） |

1. 测试侧改工具 → 开发门禁变红，责任边界糊了；
2. 违反测试独立性——被测方的门禁不应依赖测试方的资产。

**修正**：`live.mjs` 的价值（真实输出 ↔ 解析器契约）保留，但归入测试侧门禁。lead 验收时两侧都跑。

## D-14 面板嵌入方式改为「侧栏入口行 + 中心列主面板」（用户改口，推翻 PB-9）

- **结论**：面板不再是右侧栏页签，改为与 `dsh-kb` 相同的接入方式：
  - `sidebar.panellist`（list）注册入口行：`id = 'memory'`、`order = 20`、`label = '记忆'`；
  - `main`（keyed）注册面板正文：`key = 'memory'`，**必须等于入口行的 `id`**；
  - 切屏交给宿主：点入口行 → `ctx.layout.selectPanel('memory')`；插件自己不持有"是否打开"的状态。
- **理由与取舍**：
  - 用户明确要求「页面嵌入方式改成 dsh-kb 那种方式，入口按钮在侧边栏，点击页面在中间区域显示」。
  - PB-9 当年反对 `main` 的理由是「右栏 + main = 第二套渲染面」。改成 `main` 之后**右栏已整套删除**（`sidebar.footer.action`、`sidebar.right.pane.tab`、`sidebarRight`/`sidebarRightTabs` 依赖全部移除），渲染面仍是一套，PB-9 的前提消失。
  - 代价：入口不再由我们绘制（宿主的入口行只吃图标 + label），因此 PE-17（记忆关闭时不打开面板）与 PE-18（无会话时给提示）从"入口拦截"降级为"面板内呈现"——关闭态由面板正文的 closed 视图表达。
  - `main` 的组件只拿到 `renderSlot`，拿不到 `sessionId`；projectKey 改为从 `sessions.list` 快照里挑：优先 `retainedBy.mainView > 0` 的会话 cwd，没有前台会话就退到 `updatedAt` 最新的会话。
- **被否决的替代**：
  - 保留右侧栏但加一个"在中间打开"的开关 → 两套渲染面，正是 PB-9 反对的形态。
  - 用 `sidebar.footer.action` 自绘入口 + `main` 面板 → 入口行位置不受宿主管理（无法参与宿主的选中态/折叠/更多菜单），且要自己维护 active 观感。
- **生效条件 / 边界**：
  - `PANEL_ID` 同时是 `main` 的 key 与入口行的 id；两者不一致的表现是「点了没反应 + 控制台报错」。
  - 对话侧 `conversation.chat.turnTail` 的「在面板中打开」改为：`ctx.layout.selectPanel(PANEL_ID)` + 通过模块级请求把目标页签递给面板；`layout` 服务缺失时该按钮退化为无动作（不报错）。
  - `dsh.client.inject` 同步改为 `dsh-client-ui-layout` + `dsh-client-ui-sidebar`（不再需要 `dsh-client-ui-sidebar-right`）。
- **来源**：用户原话「页面嵌入方式改成dsh-kb这种方式的，入口按钮在侧边栏，点击页面在中间区域显示。」

## D-15 设置落到界面 + 新增自动召回注入（用户要求：设置上界面、增加记忆召回）

- **结论**：
  1. **设置的 UI 形态 = 页头按钮 + 抽屉**，不开第四个页签。7 项全部可见可改（含新增的 `recall_inject`），控件类型/范围来自 `src/shared/settings.ts` 单一规格表；
  2. **召回 = 自动注入**，不是新增一个检索页。开启后每轮按用户输入召回 top-3，作为宿主的 runtime-context 段注入（`SystemPrompt.context`，顺序位 130，段名 `dsh-memory:recall`）；
  3. **默认关闭**（`recall_inject=0`），且**关闭记忆时永不注入**；
  4. 抽屉里提供**召回预览**，与真实注入共用 `formatRecallText()`。
- **理由与取舍**：
  - 「页签恰三个」是 PC-01 / HC-3 的硬约束，且已有 `role="tab"` 计数断言；为了多一个设置页去改契约，代价大于收益。设置也不是「记忆的另一种视图」。
  - 抽屉在**关闭态**也要有入口，否则用户关掉记忆后在面板上无路可回。
  - 自动召回是 R-3.5.1「按需检索、不常驻上下文」的**显式例外**：用户亲手打开才生效，只带本轮输入召回的 top-3，不改 system prompt 本体；默认配置下 TC-AC1-02 的负向断言仍成立。
  - 本轮输入取法受宿主 API 限制：`AssembleContext` 只有 `{ scope, signal }`，拿不到消息；改用 `agents.currentInitiator()?.session.deriveMessages()` 倒找最后一条 `role=user && source.kind=user`。拿不到就不注入（fail-closed）。
  - 检索降级（超时/错）时**不注入**：缺条目的「半份记忆」比不注入更容易误导模型。
- **被否决的替代**：
  - 把设置做成第四个页签 → 违反 PC-01 / HC-3，且要重写一批面板契约断言。
  - 做一个「召回」页签手动输入查询 → 用户已明确选择「只提供一个召回开关在设置页，按用户输入注入上下文」。
  - 默认开启召回 → 推翻 R-3.5.1，并会让 TC-AC1-02 变成假绿。
- **生效条件 / 边界**：
  - 三个宿主服务（`systemPrompt` / `agents` / `workingDirectory`）缺任一就不注册注入；这条路径是增强，不得拖垮插件激活。
  - 快照是否每轮真的追加、空串是否被宿主过滤，尚未在运行中的宿主里验证，已在 tech-design §16.3 如实标注。
  - 顺手修掉 `decay_window_days` 「schema 播种但代码不读」的接线缺口（否则面板上这一项是摆设）。
- **来源**：用户原话「开发设置到界面上，并且增加记忆召回功能」；澄清选项「全量 6 项 + 校验」、「只提供一个召回开关在设置页，按用户输入注入上下文」。
